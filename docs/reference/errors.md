# 故障排查

| 现象 | 检查与处理 |
| --- | --- |
| 找不到 `can0` | 检查 USB-CAN、`ip -brief link show` 与实际接口名 |
| 接口 UP 但 `communication_ok=false` | 检查电源、急停、CAN-H/L、终端电阻与 bitrate，观察 RX 是否增长 |
| `pyagxarm` 安装失败 | 确认 Git 可用、GitHub 可访问，再按锁文件同步 |
| 反馈缺失、过期或格式错误 | 停止运动排查通信；不要放宽时效检查来掩盖问题 |
| 使能、关节范围或单步检查失败 | 核对反馈、目标单位及当前状态，不跳过驱动保护 |
| 运动限制无法确认 | 核对固件支持和读取结果；确认现有限制后才考虑 `--no-configure-motion-limits` |
| 端口 6001 被占用 | 检查已运行的服务；controller 托管模式与手动服务不要同时启动 |
| `--speed-percent` 被服务拒绝 | 此参数属于主 CLI 的规划运动，服务的 JS 模式不接受它 |
| 旧 `piper_x_follow.py` 不存在 | PiPER-X 客户端已迁入 controller，按[联调说明](../index.md#手动联调)连接 |

## 退出码与反馈

主 CLI 正常返回 0；已处理的操作错误返回 1；无读取结果或 argparse 参数错误返回 2。`status` 可能成功输出不完整通信状态，必须检查 JSON 字段。完整规则见 [CLI 参考](cli.md)。

## 退出和硬件状态

Ctrl+C/SIGTERM 结束服务并断开主机连接，不代表硬件回零或失能。使用 controller 时先等待其客户端退出流程完成，再关闭手动服务。失能会带来下坠风险，先支撑机械臂；电子 stop 不能替代物理急停。

报告问题请附命令、提交、Python/依赖版本、设备固件、脱敏状态 JSON、CAN 统计与完整错误，说明模拟还是实机复现。不要通过未验证的运动命令排查只读通信故障。
